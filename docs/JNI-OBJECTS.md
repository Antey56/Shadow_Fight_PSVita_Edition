# Context → AssetManager: internal object model

Добавлен jni_objects.c: ограниченная модель объектов Context и AssetManager, связанная с ранее реализованным read-only файловым backend. Host integration test получает asset manager через точное имя getAssets и дескриптор ()Landroid/content/res/AssetManager;, открывает файл и сравнивает прочитанные байты. Android-код не исполняется.

## Реализовано

- Одна среда владеет одним менеджером assets. Все ссылки на AssetManager этой среды представляют один backing manager; Context — синтетический объект.
- 64 слота ссылок, общих для локальных и глобальных. Новая ссылка получает собственный слот; удаление копии не удаляет остальные ссылки.
- 32-битный внутренний handle содержит индекс и generation. После удаления/очистки слота старый handle отклоняется даже при повторном использовании слота. При исчерпании generation слот выводится из оборота, а не переполняется.
- Очистка локальных ссылок сохраняет глобальные. Она является явной операцией тестового harness, а не реализацией PushLocalFrame/PopLocalFrame.
- Первая ошибка сохраняется до явной очистки. Пока ошибка ожидает обработки, создание ссылок и обычные вызовы возвращают отказ. Удаление ссылок и очистка локальных разрешены для освобождения ресурсов.
- Ошибки различают неверную ссылку, тип, ёмкость и неизвестный метод/сигнатуру. Неподдерживаемые методы не сообщают об успехе.

## Границы

Это **не JNI ABI**: SfJniRef нельзя передавать как jobject, а SfJniObjects — как JNIEnv. Экспорт AAssetManager_fromJava намеренно не добавлен: без настоящей таблицы JNIEnv и проверки объектов он создавал бы ложное впечатление готовности. Реальные JNI contracts и references описаны в [спецификации](https://docs.oracle.com/en/java/javase/26/docs/specs/jni/functions.html).

Модель работает только в одном потоке; идентификации потока и AttachCurrentThread нет. Handles принадлежат ровно одной среде. Их запрещено обменивать между средами: числовые значения могут совпасть. Удалённую среду использовать нельзя. Это контракт доверенного кода, а не защита от произвольных указателей гостевой библиотеки.

Код ошибки не является Java Throwable. Нет class objects, FindClass/GetMethodID, CallObjectMethod/A/V, JavaVM, строк, массивов, наследования, weak refs или сборщика мусора. Менеджер assets живёт до уничтожения среды; извлечённый указатель заимствован и после этого недействителен. Уже открытые AAsset имеют собственные файловые handles и должны закрываться вызывающим кодом.

Корень assets должен быть доверенным и неизменяемым: ограничения путей и памяти описаны в ANDROID-ASSETS.md. Модель не добавляет сохранений, ZIP openFd, Google services или проверок лицензии.

## Проверено

12 новых host-тестов: чтение через Context, неверный receiver/type/signature, pending error, устаревшая ссылка, global lifetime, ошибочное удаление, заполнение и восстановление ёмкости, NULL, копии ссылок. Всего проходят 94 Python/integration tests и 5 CTest targets; Vita cross-build успешен. На Vita модель ещё не запускалась, диагностический main её не вызывает.

Следующий барьер — отдельный JNI ABI bridge с корректной таблицей функций, методами/классами, потоком и исключениями. Затем можно связать реальный вызов Context.getAssets с этой моделью и проверить AAssetManager_fromJava. Счётчик внешних импортов и готовность запуска игры этим этапом не изменены.
